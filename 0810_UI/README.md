# AIGIS 3화면 통합 관제 UI

PPT 1~4페이지를 기준으로 만든 실제 동작용 Python UI 초안이다.

이 폴더는 단독 실행형이다. AES-GCM 코덱(`aes_gcm_128.py`), 사용자 DB(`users.json`), 이미지 자산과 실행 코드가 모두 `0810_UI` 내부에 있으며 상위 프로젝트나 RTL 폴더를 참조하지 않는다.

## 화면

1. 메인 관제: PCAM 입력을 2분할 비교 표시. CH-A는 정상 마스터키 영상이며, CH-B도 처음에는 정상 영상을 표시한다. CH-B의 `오류 MASTER KEY 적용`을 누르면 `SESSION 불일치 → GCM TAG 실패 → 프레임 폐기` 차단 화면으로 전환되고 `정상 MASTER KEY 복구`로 돌아온다.
2. 랙 감시/제어: 전체 화면을 왼쪽 1/3 `RACK CONTROL`과 오른쪽 2/3 `MONITORING`으로 구성. 왼쪽은 랙 1~4를 2×2로 배치하고 정상/가짜 마스터키 선택, 출입문·전체 랙·오류키 시험 버튼을 표시한다. 오른쪽 블록다이어그램은 각 장비 상단에 암호화/처리/복호화 동작을 가로 흐름으로, 하단에 `마스터키 ⊕ 난수키 = 세션키` 생성을 세로 흐름으로 표시한다. 랙 명령은 `관제 PC → ZYBO → Basys3`, 출입문 명령은 `관제 PC → ZYBO → Jetson` 경로로 구분한다.
3. 사용자 등록: `CAM 입력 / INFORMATION / 3D 윤곽 DATA`를 2:1:2 비율로 구성, 큰 입력 글씨와 랙 권한 2×2 선택, 얼굴 프레임 저장, 하단 완료 알림

## 실행

하드웨어 연결 전 화면 확인:

```powershell
cd D:\260807_AIGIS_inseok\0810_UI
python app.py --simulate
```

전체화면으로 바로 시작하려면 `--fullscreen`을 추가한다.

다른 PC에서는 처음 한 번 `install_requirements.bat`를 실행한 뒤, 하드웨어 연결 시 `run_hardware.bat`, 화면 확인만 할 때는 `run_simulation.bat`를 실행한다. `run_hardware.bat`의 기본 포트는 COM10이다.

ZYBO가 COM10에 연결된 실제 모드:

```powershell
python app.py --port COM10
```

화면 전환:

- 상단 `전체화면` 버튼 또는 `F11`: 전체화면/창 모드 전환
- `Esc`: 전체화면에서 창 모드로 복귀

## 실제 연결 범위

- 기존 `aes_gcm_128.py`를 그대로 불러와 AES-128-GCM 48바이트 UART 프레임을 사용한다.
- 30초 세션키 갱신과 재키잉 중 명령 큐를 유지한다.
- ZYBO의 `KEY_UPDATE`에서 받은 실제 128비트 난수를 랙 화면에 `[REKEY] ... R=...` 형태로 기록한다.
- 랙 블록다이어그램 왼쪽 위에 `MASTER KEY XOR ZYBO RANDOM R = CURRENT SESSION KEY` 실제 계산값을 표시하고 각 장비 블록 아래에 현재 하드코딩 마스터키를 표시한다.
- 화면 표기는 `마스터키 / 난수키 / 세션키`로 구분하며, 재키잉 때 난수키와 세션키를 실시간 갱신한다.
- Jetson↔ZYBO와 ZYBO↔Basys3는 `SPI`, 관제 PC↔ZYBO는 `UART`만 표기한다. TX/RX 글자는 표시하지 않고 굵고 간격이 넓은 왕복 두 선으로 나타낸다.
- 각 장비 내부의 128비트 키는 생략하거나 줄바꿈하지 않고 32자리 한 줄로 표시한다. 암호화/제어/복호화 블록은 장비 상단에서 왼쪽에서 오른쪽으로 흐르고, `마스터키 ⊕ 난수키 = 세션키`는 그 아래에서 위에서 아래로 흐른다.
- 관제 PC와 Jetson에도 동일한 키 생성 블록을 표시하며 장비 블록 폭을 통일한다. 상세 로그 화면은 운영 UI에서 숨긴다.
- `INVALID KEY 전송`은 정상 마스터키의 첫 비트를 뒤집고 현재 난수와 XOR해 잘못된 세션키를 만든 뒤 AES-GCM 프레임을 보낸다. 공격용 ALL OPEN 명령 자체는 로컬 랙 상태에 적용하지 않지만, 현재 시연 장비의 fail-safe 동작에 맞춰 UI 랙 표시는 모두 `CLOSE`로 동기화한다. 누르면 보안공격 감지 팝업을 표시한다.
- 오류키 시험 중에도 디버그용 키 비교 패널과 주황색 패킷 상태 문장은 표시하지 않고, 중앙 인증 실패 팝업과 데이터 흐름 애니메이션만 표시한다.
- 랙 화면에서 `가짜 마스터키`를 선택하면 개별 랙, 전체 랙, 출입문 명령을 PC에서 인증 실패로 차단하여 UART로 전송하지 않는다. 따라서 장비 상태와 주황색 데이터 흐름은 변경되지 않는다. 실제 잘못된 GCM 패킷은 별도의 `INVALID KEY 전송` 공격 시험 버튼으로만 보낸다.
- OV7670 비전 상태가 이상/비상으로 전환되면 4번 랙 테두리 경고와 함께 중앙 경고 팝업을 한 번 표시한다.
- 마스터키, ZYBO 난수, XOR 세션키, 평문, IV/카운터, 암호문, GCM TAG를 실제 암복호화 프레임에서 추출해 표시한다.
- 랙/출입문 명령은 기존 ZYBO/Basys3 RTL 명령 형식을 사용한다.
- 온습도, 화재 서보, 카메라 3유닛 상태를 실제 수신 데이터로 갱신한다.
- 카메라 3유닛 중 이상/비상이 있으면 OV7670이 감시하는 4번 랙을 확대하고 빨간색으로 강조한다.
- 등록 정보는 `0810_UI/users.json`에 저장한다.
- 얼굴 스냅샷은 `face_registry/<사용자ID>.jpg`에 저장한다.

## 이벤트 로그 기준

- 실제 모드: UART 연결 상태, ZYBO 재키잉 난수, AES-GCM 세션 연결, 실제 센서 상태 변화, 사용자 제어 명령만 표시한다.
- 시뮬레이션 모드: 생성된 센서/Face ID 이벤트 앞에 반드시 `[DEMO]`가 붙고 우측에도 `DEMO 데이터`가 표시된다.
- 같은 화재/비전 상태가 계속 유지되는 동안에는 매 주기마다 중복 로그를 만들지 않고, 상태가 바뀔 때만 기록한다.
- 난수 표시가 필요 없으면 `config.json`의 `show_security_random`을 `false`로 바꾼다.

## 보안 공격 시험

`INVALID KEY OPEN`은 정상 마스터키의 첫 비트를 뒤집은 뒤 현재 난수와 XOR해 만든 잘못된 세션키로 `ALL OPEN` 프레임을 암호화해 전송한다. 정상적인 ZYBO AES-GCM 수신기는 TAG 검증 실패로 공격 명령을 폐기해야 한다. 현재 시연 구성에서는 시험 직후 장비가 fail-safe CLOSE 상태가 되므로 UI의 네 랙도 `CLOSE`로 맞춘다.

마스터키를 포함한 모든 값을 표시하는 기능은 시연/디버그용이다. 운영 배포 시에는 키 상세 표시를 제거하거나 접근을 제한해야 한다.

## 랙 애니메이션과 Face ID

- 랙 명령 상태가 바뀌면 약 0.45초 동안 전면 도어 OPENING/CLOSING 애니메이션을 표시한다.
- Face ID 패킷이 들어와도 랙/등록 화면을 관제로 강제 전환하지 않는다. 관제 화면을 보고 있을 때만 중앙 Face ID 오버레이를 표시한다.
- 등록된 인가자는 초록색, 미등록/비인가는 빨간색으로 표시하며 기본 8초 뒤 두 채널 비교 화면으로 돌아간다.
- CH-A는 마스터키 불일치, 재키잉 대기 또는 GCM 인증 실패 시 차단된다. CH-B는 정상 영상으로 시작하고 버튼으로 오류 마스터키 차단 화면과 정상 마스터키 영상을 전환한다.

## 카메라 설정

`config.json`에서 입력을 지정한다.

- `face_camera_source`: PC에 연결된 얼굴 등록 카메라 번호. 기본값 `0`.
- `pcam_ch_a_source`: 정상 마스터키 채널에 대응하는 첫 번째 PCAM 번호 또는 주소.
- `pcam_ch_b_source`: 오류 마스터키 비교 채널에 대응하는 두 번째 PCAM 번호 또는 주소. `null`이면 CH-A 입력을 공유한다.
- `cctv_source`: 이전 설정과의 호환용 입력. `pcam_ch_a_source`가 `null`일 때 사용한다.
- `face_overlay_seconds`: Face ID 오버레이 유지 시간. 기본값 `8`초.

현재 Jetson의 `get_face_id()`는 테스트용 무작위 사용자 반환 함수다. 저장된 얼굴 이미지를 실제 인식 모델에 학습시키는 단계는 Jetson 얼굴인식 모델의 등록 API가 정해진 뒤 연결해야 한다. UART/RTL에는 얼굴 영상 또는 학습 데이터를 보내는 프로토콜이 없으므로 이 부분은 RTL 변경 사항이 아니라 Jetson Python 소프트웨어 연동 사항이다.
